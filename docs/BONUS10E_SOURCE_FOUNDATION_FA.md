# فاز ۱۰E-1 - پایه ادغام سورس سه شاردی (بدون استقرار)

## وضعیت پیش از این بسته

- Commit مرجع محلی GitHub: `407ef23` روی `main`.
- سرور فعلی `/opt/distributed-banking-platform` یک Deployment بدون `.git` است؛ این بسته فقط روی **Git ویندوز** اعمال می‌شود.
- سامانه اصلی A/B، هشت سرویس Healthy، Self-Healing فعال، هیچ تراکنش Prepared یا Pending ندارد.
- محیط‌های مستقل ۱۰A و ۱۰B و آزمایشگاه ۱۰C/D تأیید شده‌اند؛ **حساب‌های واقعی B هنوز منتقل نشده‌اند.**

## تغییرات این بسته

1. **نقشه شارد نسخه‌دار**: پذیرش ساختار ثابت دو شارد نسخه ۱ و ساختار پس از انتقال سه شارد نسخه ۲ یا بالاتر؛ اعتبارسنجی بدون هم‌پوشانی یا شکاف و با دو Replica برای هر شارد. فایل اصلی `config/shard_map.json` عمداً دست‌نخورده باقی می‌ماند. `config/shard_map_3shard.example.json` صرفاً مثال است و نباید به‌جای نقشه اصلی کپی شود.
2. **سورس Replica**: شناخت شناسه C1/C2 با پرچم صریح `BANK_ENABLE_SHARD_C=1`، پشتیبانی از محدوده حساب‌های C و بازه کوتاه‌شده B صرفاً در صورت تنظیم صریح. کنترل هویت PostgreSQL هنوز جلوی کار با دیتابیس نامنطبق را می‌گیرد.
3. **2PC**: امکان ساخت شناسه Prepared برای C. Coordinator به جای فرض دو ستون تأیید، شرکت‌کنندگان (دو طرف هر تراکنش) و Epoch را در جدول مستقل SQLite و **در همان تراکنش ثبت NEW** ذخیره می‌کند. تصمیم COMMIT قبلی هرگز بازنویسی نمی‌شود. Journalهای قدیمی فقط با افزودن ستون و جدول ارتقا می‌یابند؛ مسیر بازیابی A/B دست‌نخورده است.
4. **آزمون‌ها**: سازگاری A/B، سناریو B/C، ACK دیررس، تطابق Epoch، Journal قدیمی و اعتبارسنجی نقشه سه‌شاردی.

## محدودیت اساسی: این کد هنوز Online Resharding عملیاتی نیست

هنوز مکانیزم مهاجرت در Gateway و بانک اصلی فعال نشده و ارسال Epoch به مسیر Write/Prepare، DB Fencing، CDC عملیاتی، انتشار اتمیک Map، مهاجرت رسیدهای 2PC و Cutover قابل بازگشت پیاده‌سازی نشده است. فایل مثال Map نباید روی سامانه اصلی فعال شود. ارتقای SQLite journal نیز پیش از به‌روزرسانی Coordinator روی نسخه اصلی ممنوع است تا Backup آزموده‌شده در دست باشد.

## اجرای امن

1. ZIP را در ویندوز با SHA256 کنترل کنید، Extract کنید و `APPLY_ON_WINDOWS_PS51.ps1` را در PowerShell 5.1 اجرا کنید.
2. اسکریپت پیش از تغییر، `git fetch/pull --ff-only` روی `main`، تمیز بودن مخزن، HEAD=`407ef23`، و هش ۵ فایل پایه را کنترل می‌کند. سپس Branch جدید `feature/bonus10e-source-foundation` می‌سازد؛ نسخه اصلی Main را تغییر نمی‌دهد.
3. فایل‌ها روی Branch قرار می‌گیرند، Commit می‌شوند و Push Branch صورت می‌گیرد. CI/CD یا تست GitHub باید بررسی شود. در این مرحله روی VPS هیچ Build یا Docker Compose اجرا نکنید.
4. در صورت عدم تأیید CI، Branch را Merge نکنید؛ برای لغو در ویندوز صرفاً `git switch main` کافی است. Source پایدار و VPS تغییری نکرده‌اند.
