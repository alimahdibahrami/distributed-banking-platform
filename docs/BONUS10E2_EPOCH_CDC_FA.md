# فاز ۱۰E-2 ـ اتصال Epoch و CDC به مسیر واقعی کد (Source-only)

## آنچه پیاده‌سازی شد

- انتقال اختیاری `owner_epoch` از Gateway به Replica در **نوشتن محلی**، و از Coordinator به Participant هنگام **PREPARE TRANSACTION**. این فیلد از API عمومی پذیرفته نمی‌شود؛ Gateway آن را از نسخه Shard Map می‌سازد.
- ثبت `owner_epoch` و `owner_shard` با `set_config(..., true)` در **همان تراکنش PostgreSQL که موجودی را تغییر می‌دهد**. در صورت 2PC، شرط مالکیت پیش از `PREPARE TRANSACTION` کنترل می‌شود؛ `COMMIT PREPARED` روی تصمیم تاریخی احتیاجی به Epoch جدید ندارد.
- DDL افزایشی `database/bonus10e2_migration_capture.sql` برای دیتابیس‌های آزمایشی B و C: جدول کنترل مالکیت، ستون نسخه هر حساب، Trigger محدودکننده نوشتن و جدول CDC. تغییر موجودی و رویداد CDC در یک تراکنش Commit می‌شوند. در `ROLLBACK` یا `ROLLBACK PREPARED` هر دو حذف می‌شوند.
- در Trigger روی ردیف کنترل مالکیت قفل `FOR SHARE` گرفته می‌شود. تغییر Epoch باید منتظر تمام تراکنش‌های درگیر، از جمله Preparedها، بماند؛ نباید میان PREPARE و ثبت تصمیم، مالکیت عوض شود.
- در صورت خطای مشخص PostgreSQL با `sqlstate=P0001` و پیشوند `STALE_OWNER_EPOCH`، پاسخ داخلی `409 STALE_OWNER_EPOCH` صادر می‌شود؛ خطاهای نامشخص همچنان `503` هستند.

## فعال‌سازی و محدوده

- **به‌صورت پیش‌فرض همه مسیرهای قدیمی بدون تغییر هستند.** `BANK_EPOCH_PROPAGATION` به‌صورت پیش‌فرض `0` است و DDL در Docker Compose اصلی وجود ندارد.
- هر دو تغییر (کد با `BANK_EPOCH_PROPAGATION=1` و DDL روی B/C) فقط **در یک Compose مستقل** قابل آزمایش‌اند؛ در سامانه اصلی فعلی اجرا نشوند.
- ردیف `bank_migration_fence` پس از نصب DDL با `fence_enabled=false` و `capture_enabled=false` شروع می‌شود. صرف نصب DDL نه Epoch را تغییر می‌دهد، نه حسابی منتقل می‌کند.
- فاز ۱۰E-3 باید ابزار تغییر کنترل‌شده پرچم‌ها و انتقال مالکیت، مجوز DB اختصاصی و آزمون Crash را فراهم کند. تا آن زمان **پرچم‌های دیتابیس را دستی فعال نکنید**.
- C باید قبلاً دیتابیس و جدول حساب داشته باشد؛ DDL آن را ایجاد نمی‌کند.

## محدودیت مهم ترتیب CDC

`event_id` یا `BIGSERIAL` **ترتیب Commit را تضمین نمی‌کند**؛ ممکن است تراکنش T2 با ID بزرگ‌تر زودتر Commit شود. بنابراین در این طراحی **مبنای Replay، `(account_id, account_revision)` است نه `MAX(event_id)`**. نسخه هر حساب همراه با Row Lock افزایش می‌یابد و پس از Snapshot باید برای هر حساب، نسخه‌ها بدون شکاف اعمال شوند. ساخت Snapshot سازگار، بارگذاری مقصد، الگوریتم Replay نسخه‌دار و barrier برای Cutover در فاز ۱۰E-3 پیاده‌سازی و با PostgreSQL واقعی آزموده می‌شوند.

اگر Snapshot هنگام شروع جمع‌آوری رویدادها گرفته شود، نباید از شمارنده سراسری به‌عنوان نشانگر تکمیل استفاده کرد. قرارداد درست، مقایسه نسخه هر حساب و گرفتن fence تراکنشی پیش از Cutover است.

## ریسک‌های باز تا نسخه عملیاتی

۱. Gateway و Coordinator فعلاً نقشه را فقط هنگام بالا آمدن بارگذاری می‌کنند؛ انتشار Epoch میان سه سرویس و قطع عملیات در حین فعال‌سازی باید طراحی شود.
۲. مهاجرت رسیدهای 2PC، مالکیت دیتابیس، مدیریت تراکنش‌های قدیمی و Route تاریخی تصمیم‌ها هنوز کامل نیست.
۳. مجوز تغییر `bank_migration_fence` باید از نقش عادی بانک جدا شود؛ نسخه حاضر فقط قرارداد SQL را آماده می‌کند.
۴. Triggerهای SQL هنوز روی PostgreSQL زنده آزمایش نشده‌اند. تست‌های واحد و Static Contract جای آزمون واقعی و Fault Injection را نمی‌گیرند.
۵. SQL با وجود استفاده از `FOR SHARE` در مهاجرت، بدون بررسی قفل‌های Prepared روی VPS **نباید روی دیتابیس اصلی** اعمال شود.

## برنامه آزمون محیط مستقل برای ۱۰E-3

- نصب SQL روی دو DB آزمایشی، کنترل `capture=false / fence=false`، فعال‌کردن با ابزار اختصاصی.
- `deposit`، `withdraw`، `transfer_local` و `PREPARE` با Epoch صحیح باید موفق باشند و دقیقا همان تغییر موجودی و رویداد CDC ثبت شود.
- Epoch قدیمی در هر چهار مسیر باید با 409 رد شود؛ Write مستقیم SQL بدون Epoch نیز باید رد شود.
- `ROLLBACK PREPARED` نباید رویداد پایدار باقی بگذارد؛ `COMMIT PREPARED` دقیقا یک receipt و یک رویداد ثبت کند.
- Snapshot + Replay نسخه‌دار، Barrier، انتقال Epoch ۱ به ۲، Restartهای مرحله‌ای و تکرار هفت آزمایش رسمی.

**قاعده تحویل:** این Branch را به `main` ادغام نکنید و در سرور اصلی Deployment نکنید تا ۱۰E-3 و ۱۰E-4 موفق شوند.
