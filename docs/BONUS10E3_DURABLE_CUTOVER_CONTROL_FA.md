# فاز ۱۰E-3 ــ کنترل پایدار و شروط ایمنی جابه‌جایی مالکیت

## محدوده این بسته

این بسته **کد کنترل پایدار مهاجرت** و **قرارداد بازپخش مبتنی بر نسخه حساب** را به Branch توسعه اضافه می‌کند. یک آزمایشگاه تازه نیست؛ ماژول‌های آن در `bank_platform/migration` و ابزار اجرای فقط‌خواندنی آن در `scripts` قرار می‌گیرند. بسته عمداً هیچ دستوری برای تغییر دیتابیس اصلی، تغییر نقشه Gateway یا انتقال خودکار داده ندارد. **اجرای Cutover واقعی در ۱۰E-4، پس از افزودن آداپتور PostgreSQL و استقرار آزمایشی یکپارچه، انجام خواهد شد.**

مبنای Git: `feature/bonus10e-source-foundation`، ‏Commit `986cbb7`. بسته فقط روی همین نسخه، در مخزن لوکال ویندوز، اعمال می‌شود.

## چرا Journal مستقل لازم است؟

یک انتقال شامل چند پایگاه داده و Gateway است و تغییر تمام آن‌ها در یک تراکنش اتمیک عمومی ممکن نیست. به همین دلیل قبل از هر عملیات، `begin` یک Intent پایدار می‌نویسد؛ سپس بعد از اجرای مرحله توسط آداپتور مورد اعتماد، `confirm` تنها در صورت ارائه خوانش معتبر و هماهنگ از وضعیت پایدار، مرحله را به جلو می‌برد. با Restart، Intent ناتمام حذف نمی‌شود و نباید حدسی ادامه داد.

ماشین حالت: `PLANNED → SNAPSHOTTING → CATCHING_UP → FENCED → ACTIVATED → VERIFYING → COMPLETED`.

## شروط اصلی کنترل

| مرحله | شرط پیش از ثبت موفقیت |
|---|---|
| SNAPSHOTTING | CDC از قبل در مبدأ فعال و مقصد هنوز Standby باشد. |
| CATCHING_UP | Snapshot ماندگار باشد و CDC ادامه داشته باشد. |
| FENCED | B به‌صورت پایدار از نوشتن روی محدوده منتقل‌شونده منع شده باشد؛ همه Prepared و تصمیم‌های معلق مرتبط صفر؛ هیچ Gap نسخه‌ای باقی نمانده باشد؛ تعداد ۵۰۰ و Digest نسخه/موجودی دو طرف برابر باشد. |
| ACTIVATED | مبدأ همچنان Fenced؛ مقصد فعال؛ Shard Map منتشرشده در Gateway از Epoch جدید استفاده کند. |
| VERIFYING | شروط فعال‌سازی و عدم وجود Gap حفظ شود و وضعیت انتقال را بتوان خواند. |
| COMPLETED | علاوه بر شروط بالا، رکوردهای محدوده انتقالی از مالک قدیمی حذف شده باشند. |

`Observation` در این نسخه یک **قرارداد نرم‌افزاری** است و هنوز مستقیماً از PostgreSQL خوانده نمی‌شود. هر برنامه‌ای می‌تواند داده جعلی به آن بدهد؛ بنابراین `confirm` این مرحله را نباید به‌عنوان مجوز عملیات واقعی به کار برد. آداپتور مورد اعتماد باید وضعیت جدول Fence، صف Prepared، Journal هماهنگ‌کننده، Checkpoint و نسخه منتشرشده Gateway را خودش بخواند، در وضعیت مناسب قفل بگیرد و سپس عملیات را انجام دهد.

## بازپخش مبتنی بر Revision

`RevisionReplay` وضعیت هر حساب را با `(account_id, revision, balance)` نگه می‌دارد. رویداد تکراری فقط با رسید یکسان پذیرفته می‌شود؛ رویداد متناقض یا با Gap رد می‌شود. شماره سراسری `event_id` به‌عنوان ترتیب قطعی Commit استفاده نمی‌شود؛ چون در PostgreSQL ترتیب تخصیص Sequence می‌تواند با ترتیب COMMIT فرق کند. این کلاس یک **قرارداد مرجع و قابل تست در حافظه** است؛ در ۱۰E-4 باید همین قواعد با UPSERT و رسیدهای پایدار در PostgreSQL مقصد پیاده شود.

## تست‌ها و نحوه بررسی

```powershell
# Windows PowerShell 5.1 — بعد از نصب بسته، از ریشه مخزن لوکال
python -m pytest -q
```

ابزار کنترلی زیر فقط یک Journal محلی مستقل ایجاد و وضعیتش را می‌خواند، بدون هیچ اتصال بانکی:

```powershell
python scripts/bonus10e3_control_preview.py --journal D:\Temp\bonus10e3-preview.sqlite --init
python scripts/bonus10e3_control_preview.py --journal D:\Temp\bonus10e3-preview.sqlite
```

برای جلوگیری از دوباره‌نویسی، `--init` روی فایل موجود رد می‌شود. این CLI عمداً `begin` یا `confirm` ندارد؛ چون بدون آداپتور واقعی نباید از نمای CLI بتوان انتقال را جلو برد.

## موانع باقی‌مانده تا پذیرش بونوس ۱۰

1. اجرای واقعی PostgreSQL برای Triggerهای E2 روی محیط سه‌شاردی یکپارچه و اثبات عملکرد `PREPARE TRANSACTION`.
2. پیاده‌سازی Snapshot پایدار و Replay تراکنشی در مقصد همراه با رسید و بررسی Gap نسخه‌ها.
3. اتصال کنترل‌کننده به خوانش‌های قابل اعتماد PostgreSQL و Coordinator؛ ثبت Intent و آشتی‌دادن نتایج پس از Crash.
4. انتشار نقشه نسخه‌دار در Gateway و Coordinator در Cutover بدون دو مالک قابل‌نوشتن و بدون شکستن تراکنش تاریخی.
5. تأیید رگرسیون هفت آزمایش اصلی، چهار سناریوی Crash و عدم تغییر موجودی؛ سپس گزارش، Image و Release.
